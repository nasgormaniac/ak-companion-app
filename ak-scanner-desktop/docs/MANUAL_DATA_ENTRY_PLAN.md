# Manual card entry plan — current decision

The user will enter cards and choose their images manually in the installed desktop app. There is no planned import from the legacy SQLite database or legacy image directory. The legacy files remain read-only references for behavior, field options, visual identity, and code-format compatibility; their record counts are audit evidence, not a transfer target.

## User workflow

1. Install and launch Animal Kaiser Scanner. The app creates an empty local SQLite database under Electron `userData` using its own schema migrations.
2. Open Animal, Strong, or Miracle; choose Add. Enter the card name, exact eight-character code beginning with lowercase `bn`, category fields, and select an image. The form displays field-specific validation before saving; the main process validates again and enforces code uniqueness across all three categories.
3. Save the card. The app stores the image in its own userData image directory, commits the record, and shows a clear CRUD success result. On a known failure, it keeps the entered values and explains the cause. No important operation fails silently.
4. Repeat as desired. Search, category filters, rarity sorting, edit, and delete help manage the growing catalogue. There is no requirement to reproduce all 102 legacy records or preserve old IDs/timestamps.

## Form fields and defaults

| Category | Required data at creation |
|---|---|
| Animal | `nama`, `rarity` (common/bronze/silver/gold/ultra/kaiser), `gold_attack` (G/T/P), `type` (speed/multi/heavy), `card_code`, image. |
| Strong | `nama`, `rarity` (common/bronze/silver/gold), `guts_level`, `tech_level`, `power_level` (each 1–5), `aura` (none/shining/defense/burning/evil/forest/miracle), `card_code`, image. |
| Miracle | `nama`, `rarity` (common/bronze/silver/gold), `effect` (the options in `VALIDATION_BASELINE.md`), `type` (speed/multi/heavy), `card_code`, image. |

Use helpful select defaults as in the legacy forms, but allow the user to review and change them. Edit permits leaving the image unchanged. Store new IDs and timestamps generated by the desktop app. Do not add fields or UI for legacy IDs, source database paths, import sessions, row counts, or transfer reports.

## Validation and image handling

One consistent code rule applies to manual Scan and card create/edit: exactly eight characters, lowercase `bn`, six supported printable characters. The inspected legacy data includes punctuation in 88 of 102 codes; an alphanumeric-only rule would reject codes the user may type later. Saved-card Use reads the already stored code without revalidating it on each click. A database uniqueness constraint and main-process check prevent duplicate codes across categories.

Check image type and size, generate an internal filename, stage the image, and keep the record and file operations recoverable. Show a specific message for invalid code, duplicate code, unsupported/oversized image, storage failure, and database failure. Uploads must never write into the legacy project.

## Protection and completion criteria

Keep target schema versioning and ordinary database/image backup and restore planning because the manually entered data will become valuable. Those features protect the new app's data; they are not a legacy-data importer. After installation, verify that a user can add one card of each category, restart the app, see those cards and images, edit/delete safely, and use them with the local game. The user then enters any further cards at their own pace. The app must work with a fresh empty database and give a helpful empty catalogue state.
